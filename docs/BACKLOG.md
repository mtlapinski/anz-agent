# Backlog

Deferred items — not scheduled, but should be picked up by whoever (human or model) is next looking for follow-on work in this area.

- **2026-07-20 — Fuzzy matches aren't persisted as aliases.** When a query fuzzy-matches an existing cached entry via the judge (`tools/cache.py`'s `lookup()`), the new query's results are returned but the new query itself is never stored. Repeating that same reworded query later still misses the exact-match fast path and re-invokes the judge every time, rather than being remembered as an alias of the original entry. Storing the new query as its own row pointing at the matched entry's results would collapse repeat lookups to the fast path, at the cost of propagating a wrong match if the judge ever errs. Compounds with the candidate-pre-filtering gap above at scale. Flagged in the final whole-branch review of the search-cache implementation.
- **2026-08-06 — Vector similarity search for the cache judge.** Even with candidate pre-filtering (see [docs/superpowers/specs/2026-08-06-local-scaling-environment-design.md](superpowers/specs/2026-08-06-local-scaling-environment-design.md)), the cache judge still costs one LLM round-trip per cache miss. Replacing it with embedding-based similarity search would remove that round-trip and scale further, but needs an embedding source decided first (external API vs. a local model) with no clear low-effort local answer yet. Lives in `tools/cache.py` / `tools/cache_judge.py`.
- **2026-08-07 — No connection pooling for Postgres; single-connection checkpointer serializes all checkpoint I/O.** The LangGraph Postgres checkpointer (`graph.py`'s `build_graph()`) holds one connection guarded by an internal lock, so every checkpoint read/write across every concurrent request serializes on it. Separately, `tools/session_store.py` and `tools/cache.py` each open a fresh Postgres connection per call with no pooling — a single `/chat` request with a cache miss opens roughly three separate connections (session lookup, cache lookup/store, checkpointer). Both are correct today but become a real throughput ceiling at concurrency beyond what this local Phase-1 environment exercises. Fix: a shared `psycopg_pool.ConnectionPool`, which `PostgresSaver` also accepts directly (`PostgresSaver(pool)`) — one pool could serve all three call sites. Flagged in the final whole-branch review of the local-scaling-environment branch as the natural first item for a Phase 2 (managed cloud deploy) design pass.
- **2026-08-08 — Service-to-service auth for `app-* → judge` if deployed off a single Docker host.** The standalone cache-judge service (see [docs/superpowers/specs/2026-08-08-cache-judge-agent-boundary-design.md](superpowers/specs/2026-08-08-cache-judge-agent-boundary-design.md)) has no auth in v1 — it relies on same-Compose-network trust with no host port exposed, matching `postgres`'s existing trust model. If `judge` is ever deployed to separate infrastructure *before* AWS Bedrock AgentCore is in the picture, the plan is network-boundary auth (restrict `judge`'s security group to accept inbound only from the app tier's security group) rather than an application-level shared secret — cheaper, not spoofable the way a leaked token is, and proportionate to the low sensitivity of what's being sent (a search query string and a shortlist of cached queries). Becomes moot once AgentCore hosts it, since IAM handles invocation auth instead.
- **2026-08-08 — Provider-neutral tracing facade.** `agent.py` and `tools/cache_judge.py` both call the Langfuse SDK directly (`start_observation`, `create_score`, etc.) via a shared `tracing.get_langfuse()` client singleton (see the same design doc above). That singleton dedupes client *construction* but not the SDK calls themselves — swapping tracing providers would still mean touching every call site. Deferred because no provider swap is currently planned; would mean wrapping those operations behind our own provider-neutral functions if it's ever needed.
